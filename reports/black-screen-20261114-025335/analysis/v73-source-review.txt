A. MAIN FINDINGS

1. Definite defect: the new framebuffer submitter metadata is captured but then lost at the logging boundary.
Active source: thor-out/build-tree/.cache/xnu-work/iokit/Kernel/MiniIOMobileFramebuffer.cpp.
- 247–251 add a per-slot name and PID.
- 909–913 choose the slot, proc_selfname/proc_selfpid in the synchronous SwapEnd/present caller context, then copy the payload. Capture happens under the queue lock.
- 957 declares a separate static swap buffer.
- 965–968 copy the queued payload into that separate buffer and call show(swap, surfaces).
- 1153–1157 nevertheless try to recover a queue slot by testing whether show()'s swap pointer lies inside fSwap[].
The passed buffer is not fSwap[]. Under the expected address-range test, this falls through to who=-1, submitter=? pid=-1. Comparing unrelated object pointers is also not a sound portable provenance scheme.
This is an instrumentation defect, not evidence that it newly causes the screen to go black. The frame drawing/clear branch is otherwise retained.
Small correction: while holding fSwapLock, copy payload, surfaces, submitter name and PID from the SAME slot into a bounded per-frame snapshot, then pass the copied identity explicitly to show(). Do not recover ownership from the copied payload address. Retire the same queued slot only after show returns, preserving the existing surface lifetime and fence behavior.
Runtime acceptance: EMPTIED should carry a real submitting user PID/name. If this build reports ?/-1, it matches the source defect and still does not identify the upstream process.

2. Partial improvement: original exit reason is sampled before corpse construction, but it is not a Console diagnostic.
Active source: xnu-work/bsd/kern/kern_exit.c:1928–1950, proc_prepareexit().
New exact-name targets include Preferences, audiomxd, mediaremoted, PosterBoard, fairplayd.A2 and a com.apple.migrat prefix.
A bounded 768-byte stack record contains name, PID, WTERMSIG(rv), WEXITSTATUS(rv), reason namespace/code and at most 512 description characters. The location is before task_mark_corpse, so corpse-allocation failure cannot prevent the attempt.
However, it calls only pong_ramoops_diagnostic_write(). There is no printf/IOLog/Console fallback here. No raw rv, explicit reason-present flag, original ut->uu_exception/uu_code/uu_subcode, timestamp, or actual task_mark_corpse return code is included.
signal/status should not both be interpreted as independent valid exit outcomes: use the raw wait status and the applicable WIF predicates in an improved record. namespace=0/code=0 can currently mean no reason object.
Small correction: keep bounded formatting and unchanged termination handling; add raw original fields and a clearly distinct corpse-result marker, and emit the same bounded text through the existing captured Console path. No increase/disable of corpse limits is justified by these messages.

- 2568: "wake scheduled on main queue +10s" is emitted immediately BEFORE dispatch_after_f at 2569. Strictly this proves reaching the scheduling site, not completion of the scheduling call.

B. RAMOOPS / PMSG LOCATION AND CAPTURE LIMIT

Current source: xnu-work/osfmk/arm64/pong_ramoops_console.h.
- Lines 7–12: physical base 0x85200000, first Console region 0x200000 bytes, total reserved 0x400000 bytes, header 12 bytes, magic 0x43474244.
- Diagnostic/pmsg region: [0x85400000, 0x85600000), size 0x200000; data starts 0x8540000c and capacity is 0x1ffff4.
- Header is three little-endian native u32 fields sig/start/size. This writer appends, does not wrap, and sets start=size=number of data bytes.
- Lines 125–126 map the fixed 4 MiB with ml_io_map_wcomb. This is a hardcoded source address, not a runtime search for a Recovery DT node.
- repo dts/pong.dts:48 reserves the matching 4 MiB as region33@85200000 with no-map. The Recovery kernel's actual DT/RAM ownership still must be checked independently before any raw physical-memory reading.
- Diagnostic writes clean the data and header to PoC and execute dsb sy. They return silently if mapping absent, invalid length or recorder busy; when full they preserve the earlier data and accept no more bytes.
- Init resets the first-region header and writes a diagnostic READY record at the beginning of the second region. This is DRAM persistence across a compatible warm reboot only if the bootloader/Recovery preserve the area. It is not nonvolatile persistence, nor a guarantee that this device's reboot path retained it.
- The code comments expect Linux to expose pmsg-ramoops-0. No alternate raw-memory exporter was found in the narrowly checked project scripts. Empty pstore does NOT establish that the bytes are still present or absent at the physical address; do not claim original exit reasons are retrievable until the capture succeeds and headers validate.
- A later Darwin boot can overwrite the previous diagnostic region's beginning/header; preserve a found raw region before testing any further boot.
No device operation was performed in this review.

E. CURRENT RECOVERY EVIDENCE UPDATE — CAPTURE / 2026-11-14

The parent capture task verified the following on the attached device in the same Recovery boot, and saved recovery-ramoops-layout.json plus properties.json with the capture. This source-review agent did not access the device.

Recovery reserved-memory node: ramoops@0xa7000000.
reg hex: 00000000a70000000000000000400000.
Decoded base=0xa7000000, total size=0x400000 (4 MiB), console-size=0x200000 and pmsg-size=0x200000; bound platform device is a7000000.ramoops.
/proc/iomem reports 0x85200000–0x856fffff as System RAM, while 0xa7000000–0xa73fffff is reserved. /dev/mem is absent. The captured pstore is empty.

This establishes a concrete address mismatch:
- Current Darwin source writes the Console at 0x85200000 and the diagnostic/pmsg buffer at 0x85400000.
- The current Recovery ramoops exporter is bound to a different 4 MiB region beginning at 0xa7000000 (its configured second 2 MiB would start at 0xa7200000).

Therefore the intended Darwin-write -> warm-reboot-retention -> Recovery-pstore-export chain has NOT been established. Empty pstore cannot be used as evidence that the new PONG EXIT code did not execute. Conversely, it is not evidence that usable old bytes remain at 0x85400000: that area is classified as ordinary RAM by this Recovery, but no raw-byte read or overwrite event was observed. Do not claim the diagnostic bytes were definitely overwritten.

Do NOT directly change Darwin's hardcoded address to Recovery's address. First establish a single board-correct reserved-RAM contract across the actual loader, Darwin memory map/allocators and Recovery DT, including region ownership, size, overlap exclusions and warm-reboot behavior. A numerically matching address is insufficient if one boot stage can allocate or overwrite it. No source/firmware change is proposed as an immediately safe address substitution.

The smallest immediate observation improvement remains a bounded Console mirror of the original exit-reason record, using the already captured Console path, while the persistence layout is corrected and independently qualified. This is a recommendation only; no source edit was performed.
